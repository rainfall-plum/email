# 用户名 JSON 导入与管理员账户

## 用户名文件与接口

管理员通过 `POST /api/mailboxes/import-usernames` 上传 multipart/form-data 的 `file` 字段。
文件必须为 `.json`、UTF-8 编码，最多 1 MiB、1,000 项；请求体在 multipart 解析前另有
1 MiB + 64 KiB 总大小限制。唯一支持的顶层字段为 `usernames`，不接受文件指定域名：

```json
{
  "usernames": ["alicewang", "jacksmith88", "testmail2026"]
}
```

用户名严格为 1–64 个小写 ASCII 字母或数字，不自动转小写、不删除空白；所有校验在后端重复执行。
文件扩展名、JSON/UTF-8 解析、结构、空数组、数量错误会拒绝整个请求；非法用户名按条目返回原因。
上传文件不永久保存，处理结束关闭上传资源。

## 与原名字库兼容

原四个 JSON 文件保存 first/last 组成名，而非完整用户名。原批量生成仍按两个 available 数组
对应下标拼接，并在冲突时追加数字。完整用户名导入不拆分姓名、不消耗或写入这四个组成名文件。

导入按以下规则分类：

1. 非法格式、空字符串、超过 64 字符：`invalid_format`、`empty_username`、`too_long`。
2. 有效字符串在本文件再次出现：`duplicate_in_file`。
3. 数据库中已有邮箱：`already_exists`，不覆盖原邮箱。
4. 已导入完整用户名或 used 池匹配：`already_used`。
5. available 池匹配：`already_available`。
6. 其余条目生成邮箱，域名只来自服务器配置。

available 匹配包括原始 first/last 条目和按位置拼接结果。used 数组会分别去重，无法可靠还原
历史配对，所以保守匹配原始条目以及任意 first+last 组合；实现按用户名拆分查集合，不构造笛卡尔积。

新增 `import_usernames` 表保存完整用户名，`username` 有唯一索引。该表与四个名字池独立；
删除邮箱也不删除已用记录，因此再次导入仍得到 `already_used`。

## 事务与错误处理

重复/非法条目逐项拒绝，所有有效邮箱、完整用户名已用记录和生成统计在一个数据库事务内提交。
任一数据库异常导致该次所有有效项回滚。并发唯一约束冲突返回安全的 409 `import_conflict`，
可以重新上传；邮箱 `local_part` 与 `email_address` 的现有唯一约束继续生效。

响应包括 `total`、`success_count`、`duplicate_count`、`invalid_count`、`existing_count`、
`created_mailboxes` 与 `rejected_usernames`。`existing_count` 合计三个 `already_*` 分类；
每个被拒条目均附原因和可读提示。非字符串项的 `username` 返回 null，避免回显嵌套对象。

导入不会更新组成名池，因此不受组成名池写入失败影响。读取池失败时拒绝本次导入，不生成任何邮箱。
日志仅记录操作、管理员 ID、数量、分类及异常类型，不记录文件内容、SQL 参数或凭据。

## 原批量生成的异常补偿

修复原有“先提交数据库，再写名字池”的顺序：现在先 flush 数据库，再更新名字池，最后 commit。
名字池写入异常时尝试恢复四个文件快照并回滚数据库；commit 异常时回滚并恢复文件快照。
同一应用进程中的批量生成与导入池快照读取使用锁协调。

这属于普通异常补偿，**不是数据库与文件系统之间的崩溃原子事务**。突然断电、进程被强制终止，
或磁盘持续故障导致恢复写入也失败时，组成名池仍可能需要管理员检查恢复。锁也不协调多个应用进程。
部署继续使用现有单应用进程模式。新用户名导入的核心状态全部存在 SQLite 同一事务中，无此跨资源限制。
